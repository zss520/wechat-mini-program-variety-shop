## 1. 非功能需求

### 1.1 性能

| 指标 | 要求 | 实现要点 |
|------|------|----------|
| 小程序首页可用 | 首屏关键数据 ≤ 2s（4G 常规） | `/home/*` 分块并行 + `/bootstrap`，图片 CDN、合适压缩 |
| 商品列表 | 分页接口 ≤ 1.5s | 索引 `(on_sale, category_id, sort)`；综合排序可用 `(on_sale, heat_score)` |
| 埋点上报 | 不阻塞主路径；单次 `/events` ≤ 200ms P99（可异步落库） | 批量 insert、校验后即返回 |
| 支付 | 下单到拉起支付 ≤ 3s（不含用户输入密码） | 微信统一下单超时设置、避免同步压缩大图 |
| 并发 | 设计目标同时在线 ≥ 500 | 200 SKU + 单店，单机 Node + MySQL 足够；连接池、无 N+1 |
| 可用性 | ≥ 99.5%（按月，不含微信侧故障） | 进程守护、磁盘与 MySQL 监控 |

管理端表格操作在 1000 条订单内翻页应流畅；不在一期做亿级分析。

### 1.2 安全

| 项 | 要求 |
|----|------|
| 传输 | 全站 HTTPS |
| 支付 | 微信 APIv3 验签；回调幂等；密钥不进小程序 |
| 密码 | 管理员 bcryptjs，复杂度至少 8 位（产品可提示） |
| 数据 | 手机号脱敏展示；备份加密或限制访问 |
| 权限 | app / admin 路由隔离；IDOR 防护（订单 user_id） |
| 上传 | 类型白名单、大小限制、随机文件名 |
| 依赖 | lockfile；定期关注微信与 Node 16 安全通告 |
| 日志 | 审计：登录、改价、退款、改加权（P1 表，P0 至少文件日志） |
| 分析数据 | 事件无 PII；90 天明细；防刷曝光；管理端不默认开放用户轨迹 |

Node 16 已 EOL：**生产暴露面应尽量小**（管理端不公开收录、防火墙），并规划 Node 18 升级窗口。

### 1.3 兼容性

**小程序：**

- iOS 12+、Android 8+（随微信客户端）
- 微信 **8.0.0+**
- 基础库 ≥ 2.32.0
- 适配常见宽度 320–428pt；核心按钮高度 ≥ 44px；正文字号不小于 14px，价格可更大

**管理端：**

- 桌面 Chrome / Edge / Firefox 近两个大版本
- 设计宽度 1280+
- 构建目标 ES2019/ES2020，避免把 Node 18 语法打进包（Vite 4 + 正确 target）

**运行时：**

- 开发、CI、生产构建：**Node.js 16.17.0**
- 管理端栈：Vite 4.5.x + React 18 + TypeScript + MUI v5（见技术方案版本表）

### 1.4 易用性

- 小程序：核心购买三步心智；老年用户可读；失败可联系店主
- 管理端：中文、确认框、表格筛选；店主无培训能上架与核销
- 无障碍：管理端依赖 MUI 组件焦点；小程序保证对比度（价签与底色）

### 1.5 可维护性

- TypeScript 覆盖 admin 与 server；小程序推荐 TS
- 文档与代码同库 `docs/`
- 环境变量示例 `.env.example`（无密钥）
- 接口变更同步更新 `05-数据模型与接口设计.md`

### 1.6 合规（上线门禁）

- 小程序类目与营业执照（个体工商户）
- 用户隐私保护指引、隐私接口声明（头像、手机号、位置若用）
- 微信支付商户号与小程序 appid 绑定
- 不收集与业务无关的个人信息
- 隐私协议须包含「用于商品展示优化与经营分析的行为数据」；分析事件不含手机号、openid

## 2. 测试要求

### 2.1 必须手测的主路径

1. 上架商品 → 小程序可见 → 加购 → 支付（开发环境可用微信支付沙箱 / 测试商户）→ 店主备货 → 核销自提码 → 完成。
2. 待付款超时关单，库存恢复。
3. 待备货顾客取消，退款与库存恢复。
4. 库存为 1 时两人同时下单，仅一单成功（并发）。
5. 管理端改价后，未刷新的预览单提交应失败或按新价（与 PRD：价格变化 409）。
6. Node 16.17.0 下 `admin` `build`、`server` `build`。
7. 首页推荐卡可见 ≥300ms 后库中有 `goods_expose`；点击详情有 `goods_click`。
8. 支付成功后杀掉小程序，商品分析购买件数仍增加。
9. 加权 +20 后综合序立即前移；推荐位置顶与预览一致。

### 2.2 建议自动化（不阻塞一期文档）

- server：库存扣减与状态机单测
- server：热度公式与 CTR 样本不足分支
- admin：登录与路由守卫组件测试（可选）

无浏览器环境时，可用接口脚本 + 微信开发者工具预览作为验证手段。

## 3. 项目里程碑

本项目为 **定制开发**（非 SaaS 套模板）。下列为研发阶段，不是对外经营承诺。

| 阶段 | 主要工作 | 交付物 |
|------|----------|--------|
| M0 需求冻结 | 本文档定稿 | `docs/` V1.1（含埋点与推荐位） |
| M1 工程骨架 | monorepo、Node 16 锁版本、空页面跑通 | 可启动的 miniprogram / admin / server |
| M2 商品域 | 分类、商品、上传、小程序列表详情 | P0 货架 |
| M3 交易域 | 购物车、订单、支付、库存、关单；**同时接入 P0 埋点与支付侧统计** | 可支付且事件落库 |
| M4 履约域 | 自提码、后台核销、配送状态 | 店主可作业 |
| M5 配置与内容 | 店铺设置、轮播、联系店主 | 可换店名开张 |
| M6 打磨上线 | 隐私、类目、支付进件、体验优化 | 审核包 + 管理端部署 |
| M7 运营迭代 | 商品分析看板、热度、权重、首页推荐位、漏斗、订阅消息 | 店主可调货架 |

P2（拼团、秒杀、多门店、详情关联推荐）不列入一期里程碑。

阶段如何拆任务、三端如何并行、R1/R2 如何切片，见 **[项目开发计划](./08-项目开发计划.md)**。下文仅保留里程碑总表与建议顺序。

### 3.1 建议实现顺序（开发）

1. 服务端用户 / 管理员登录 + 店铺 bootstrap  
2. 管理端布局 + 商品 CRUD  
3. 小程序首页 / 分类 / 详情  
4. 购物车 + 创建订单 + 库存  
5. 微信支付 + 回调  
6. 订单列表 / 详情 / 取消 / 超时任务  
7. 自提码核销 + 配送流转  
8. 轮播与设置  
9. P0 埋点验收（曝光/点击/支付服务端记账）  
10. 体验与安全扫描  
11. P1：商品分析、权重、首页推荐位

## 4. 运营建议（上线后）

### 4.1 启动（第 1–2 周）

1. 先上架 50–100 个高频商品，实拍、准库存。  
2. 店内张贴小程序码（收银台、货架、袋装）。  
3. 首单优惠（P1 券；P0 可用店主口头 + 特价商品）。  

### 4.2 增长（第 3–8 周）

1. 微信群发链接与品类活动。  
2. 上线积分 / 会员价（P1）。  
3. 固定档期满减（P1）。  

### 4.3 成熟（第 9 周起）

1. 看商品分析：高曝光低转化改图/改价；热度高补货。  
2. 用权重和首页推荐位代替「全靠手改 sort」。  
3. 低库存预警减少空卖。  
4. 增值（代收快递等）不进系统也可线下做，避免一期膨胀。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| Node 16 EOL | 安全补丁停更 | 缩小暴露面；列入升级 Node 18 + Vite 5 技术债 |
| 微信审核 / 类目 | 不能发布 | 提前准备资质；开发版继续联调 |
| 支付进件慢 | 不能收款 | 先跑通下单关单，支付用沙箱 |
| 店主不维护库存 | 超卖投诉 | 售罄展示清晰；核销前可改库存；教育为主 |
| 配送成本 | 利润被吃掉 | 默认自提；配送费 / 起送价可配 |
| 大平台比价 | 流失 | 强调邻里与即时自提，不拼全网最低价 |
| 并发超卖 | 客诉 | SQL 条件更新；单测 |
| 依赖误升 Vite 5 | 16.17.0 无法构建 | engines 字段 + CI 用 16.17.0 镜像 |
| 刷曝光导致热度失真 | 推荐位被刷 | 客户端去重 + 单日截断 + IP 限流 |
| 样本少误判滞销 | 错下架新品 | 样本不足不惩罚、新品 72h 排序保护 |
| 只信客户端支付事件 | 购买率偏低 | 支付回调写统计 |
