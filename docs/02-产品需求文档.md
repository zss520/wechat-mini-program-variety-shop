## 1. 产品概述

### 1.1 产品名称

【待定】建议格式：`{店铺名}社区杂货铺` / `{店铺名}便利店`。

系统内部代号：**variety-shop**（与仓库 `wechat-mini-program-variety-shop` 对齐）。

小程序展示名、管理后台系统名可分别配置，不写死在代码里。

### 1.2 产品定位

面向社区居民的轻量化线上购物工具，为社区杂货铺提供：

**商品展示 → 在线下单 → 微信支付 → 到店自提 / 店主配送 → 会员与复购**

的一站式数字化经营能力。

一句话：**把线下货架搬到微信里，把微信群里的口头订单变成可追踪的系统订单。**

### 1.3 产品目标

| 编号 | 目标 | 一期衡量方式（建议） |
|------|------|----------------------|
| G1 | 24 小时云货架，顾客不到店也能看清有什么、多少钱 | 在售 SKU 可在小程序检索；库存售罄不可下单 |
| G2 | 承接微信群 / 店内扫码流量，形成下单闭环 | 订单 100% 来自小程序支付或店主代下（若有） |
| G3 | 降低人工接单、错单、漏单 | 订单状态可追踪；待处理订单有列表 |
| G4 | 沉淀会员，提升复购与客单价 | 用户与订单绑定；P1 上线积分 / 券 |
| G5 | 店主可独立完成日常经营，不依赖开发 | 管理端完成商品 / 订单 / 基础配置 |

### 1.4 适用场景

- SKU **≤ 200**（架构上不写死，但交互与性能按此设计）
- 月营收约 **50 万以下** 的单店
- 社区便利店、日用百货、小型超市
- 单门店、单仓库（一期不做多门店库存隔离）

### 1.5 产品原则

1. **真实库存**：只卖店里有的；售罄必须可见、不可超卖（允许短暂超卖窗口，见业务规则）。
2. **路径要短**：核心购买「浏览 → 加购 → 结算 → 支付」控制在三步心智内。
3. **自提优先**：默认履约是到店自提；配送为可选项。
4. **店主可联系**：任何订单卡顿都能打电话 / 复制微信号，避免「只有机器人」。
5. **一期克制**：拼团、秒杀、多门店、第三方配送、直播不进 P0。

## 2. 范围

### 2.1 一期包含（In Scope）

| 端 | 范围 |
|----|------|
| 小程序 | 登录（微信授权）、首页、分类、搜索、商品详情、购物车、下单、微信支付、订单列表 / 详情、取消订单、地址、自提码、个人中心、联系店主 |
| 管理端 | 登录、商品与分类、上下架、订单处理、基础店铺配置、轮播图、管理员账号 |
| 服务端 | 上述业务 API、微信登录、支付回调、订阅消息（P1 可先留接口） |
| 数据 | 单店商品、订单、用户、地址、库存流水（最小集） |

### 2.2 一期明确不做（Out of Scope）

| 项 | 说明 |
|----|------|
| uni-app / Taro / H5 商城 | 顾客端仅微信原生小程序 |
| SaaS 模板搭建 | 本项目按定制自建交付 |
| 多门店、多仓、加盟 | 一期单店 |
| 社区团购主模式、供应商门户 | 不做 |
| 拼团 / 秒杀 | P2，见功能清单 |
| 骑手 App / 第三方运力 | 配送员角色为可选，一期由店主在后台改状态即可 |
| 智能推荐算法 | P1「推荐」可用热销 / 人工推荐位，不上个性化模型 |
| 小程序直播、视频号带货 | 不做 |
| 管理端移动 App | 管理端为 Web；店主可用手机浏览器应急，但不单独做 App |

### 2.3 优先级定义

| 级别 | 含义 | 一期发布 |
|------|------|----------|
| **P0** | 没有则无法开业 | 必须交付 |
| **P1** | 显著提升复购或店主效率 | 一期力争，可排在 P0 稳定之后的迭代包 |
| **P2** | 增强运营玩法 | 二期及以后 |

## 3. 用户角色

| 角色 | 端 | 说明 |
|------|----|------|
| 顾客（普通用户） | 小程序 | 浏览、加购、下单、支付、自提 / 收货、查看订单 |
| 店主 / 管理员 | Web 管理端 | 商品、订单、会员、营销、数据、店铺配置 |
| 配送员 | 可选 | 一期不单独端；如需要，由店主在后台把订单标为配送中 / 已送达 |
| 系统 | — | 支付回调、超时关单、库存扣减 |

权限模型一期采用 **管理员（可配置多个）+ 顾客**。不做复杂 RBAC；预留「角色」字段，P2 再拆「仅看订单 / 仅改商品」。

## 5. 业务规则（产品级）

### 5.1 价格与库存

1. 售价以分为单位存储，展示为元，避免浮点误差。
2. 下单锁库存：支付成功（或「货到付款」若未来支持）后扣减；一期仅在线支付，**创建待付款订单时预占库存，超时或取消释放**。
3. 库存为 0：小程序展示售罄，不可加购。
4. 店主后台改库存：不得把库存改为负数；已预占数量需在界面提示（P1）。
5. 特价（P1）：下单时校验活动未过期，否则按原价或拦截并提示。

### 5.2 订单与支付

1. 仅微信支付；不支持货到付款（一期）。
2. 待付款超时默认 **15 分钟** 关单并释放预占。
3. 支付回调与查单对账：以微信结果为准，防止重复入账。
4. 顾客取消：
   - 待付款：直接关闭，释放库存。
   - 待备货（已支付未备货）：允许取消，走退款（原路退回），释放库存。
   - 已备货 / 配送中：顾客不可自行取消，展示「联系店主」。
5. 店主取消已支付订单：必须退款成功才将订单置为已取消。

### 5.3 履约

1. 自提：店主点「备货完成」后状态为待自提；核销提货码（输入或扫码）后完成。
2. 配送：店主点「开始配送」→ 配送中；「确认送达」→ 已完成。一期不做地图轨迹。
3. 配送费：可配置固定运费；满额免运费（P1）。

### 5.4 账号与隐私

1. 顾客身份以 `openid` 为唯一键；`unionid` 如有则存储。
2. 手机号仅在用户主动授权后保存。
3. 管理端手机号、openid 不对普通员工展示完整 openid。
4. 操作日志：登录、改价、退款至少记录（P1，P0 建议有服务端日志）。

### 5.5 内容与审核

1. 商品图由店主上传，需告知不得侵权。
2. 小程序类目按「电商平台 / 生活服务-百货」等实际类目申请；虚拟商品一期不卖。

## 6. 用户故事（节选，P0）

1. 作为顾客，我希望在小程序里按分类看到店里在卖的商品和价格，以便决定买不买。
2. 作为顾客，我希望把多件商品放进购物车一次结账，以便少付几次款。
3. 作为顾客，我希望用微信支付，并选择下班后到店用提货码取货。
4. 作为顾客，我希望看到订单是否已经备好，以免空跑一趟。
5. 作为店主，我希望在电脑上架商品、改价格和库存，以便和货架保持一致。
6. 作为店主，我希望有待处理订单列表，备完货点一下，以免微信里翻聊天记录。
7. 作为店主，我希望顾客到店报提货码，我核销后订单完成，以免拿错货。

## 7. 业务流程（产品视角）

### 7.1 顾客购物

```
打开小程序 →（按需登录）→ 浏览 / 搜索 → 加购或立即买
→ 确认订单（自提或配送）→ 微信支付
→ 待备货 → 店主备货
→ 自提：待自提到店核销 | 配送：配送中至送达
→ 已完成
```

### 7.2 店主处理

```
后台看到新订单（已支付）→ 按清单备货打包
→ 自提：标记备好（P1 通知顾客）→ 核销提货码
→ 配送：开始配送 → 送达
```

### 7.3 社群闭环

```
微信群发商品 / 活动 → 打开小程序 → 下单支付
→ 自提进店（可产生额外线下购买，系统不强制记录）
→ 会员与复购（P1）→ 下次活动再触达
```

## 8. 界面设计要求（产品）

### 8.1 小程序

- 简洁、价签醒目、按钮足够大（兼顾老年用户）。
- 品牌色由店铺配置，默认温暖暖色（如琥珀 / 朱红），忌信息过载。
- 核心页：首页、分类、详情、购物车、确认订单、订单详情、个人中心。
- TabBar 建议：首页、分类、购物车、订单、我的（五项内；若五项超限则订单放「我的」内，Tab 为首页 / 分类 / 购物车 / 我的）。

### 8.2 管理端

- Material UI 默认主题可定制主色，使用 `CssBaseline` + 中文字体栈。
- 表格：密度 `comfortable`，筛选与操作按钮层级清晰。
- 关键操作（退款、删除商品、下架）需确认对话框。
- 适配桌面宽度 ≥ 1280px 为主要场景；平板可用；不把手机作为管理端主设计目标。

## 9. 成功标准（一期上线）

必须同时满足：

1. 顾客可完成：浏览上架商品 → 加购 → 支付 → 生成自提订单。
2. 店主可完成：上架商品 → 看到订单 → 备货 → 核销自提。
3. 支付与库存：支付成功库存减少；取消 / 超时库存恢复。
4. 微信审核所需的隐私协议、类目、支付开通路径在实施计划中列出，不阻塞开发联调（可用沙箱）。

P1 不作为一期 Go-Live 硬门槛，但应在架构上留表结构与菜单位。
