## 0. 对现有需求的深度分析（为何要补这一层）

### 0.1 V1.0 已经说清、但无法运营的缺口

| V1.0 表述 | 缺口 | 后果（若不补） |
|-----------|------|----------------|
| 产品目标 G4「沉淀会员、提升复购与客单价」 | 没有漏斗指标，无法判断是「没人看」还是「看了不买」 | 店主只能凭感觉改价、改图 |
| 首页「推荐商品」P1：热销或后台推荐位 | 未定义热销、未定义坑位、未定义与人工置顶的关系 | 开发会做成「sold_count 倒序」，新品与高转化低销量商品永远沉底 |
| 分类默认排序：`sort` + 上新 | `sort` 全靠手填，与真实兴趣脱节 | 200 个 SKU 时店主不可能每天调序 |
| 数据统计 P1：销售额、热销 TOP | 只有结果（卖了多少），没有过程（曝光→点击→加购→支付） | 无法发现「高曝光低转化」的死图 / 错价商品 |
| 社群引流闭环 | 没有场景 / 来源（扫码、分享、搜一搜） | 不知道群链接是否真的带来订单 |
| Out of Scope：「不上个性化推荐模型」 | 正确，但被误读为「不做推荐」 | 丢掉社区店最需要的 **规则推荐 + 人工置顶** |

**结论：** 一期仍 **不上机器学习个性化**。必须上的是：

1. **采集**：小程序核心漏斗事件（上线即采，否则历史不可补）。
2. **度量**：按商品的曝光、点击率、加购率、购买率、热度。
3. **干预**：人工权重、推荐位（置顶 + 热度补齐）。
4. **排序**：列表「综合」默认结合热度与权重，售罄沉底。

这与调研中的「邻里货架数字化」一致：店主原来靠手摆货架，线上对应的是 **坑位与权重**；原来靠目测人气，线上对应的是 **热度与转化率**。

### 0.2 社区杂货铺场景下的度量原则

1. **店主能看懂**：展示「次数 / 人数 / 率」，热度用 0–100 分，避免黑盒。
2. **过程与结果拆开**：点击率低改卡片（图、名、价）；购买率低改详情或价格；热度高但库存紧则预警补货。
3. **支付转化以服务端为准**：购买率禁止只信客户端 `pay_success`，必须用支付回调 + `order_items`。
4. **SKU 少、样本小**：7 日窗口为主、30 日为辅；人数分母 &lt; 10 时率值标记「样本不足」，不参与自动排序或降权。
5. **采集与看板解耦**：P0 埋点随交易上线；看板 / 权重 / 推荐位为 P1，但表结构 P0 预留。

### 0.3 与微信官方统计的关系

| 能力 | 用途 | 能否替代本需求 |
|------|------|----------------|
| 微信公众平台「数据分析」 | 访问趋势、页面、停留，审核与宏观观察 | **不能**。无商品 ID 级 CTR/CVR，不能驱动推荐位 |
| `wx.reportEvent` / 自定义分析 | 在微信后台看漏斗（需在 MP 配置事件） | **补充**。与自有埋点双写核心事件 |
| 自有 `POST /api/app/events` | 商品级运营、热度、排序、推荐 | **主路径** |

本项目以 **自有埋点为运营数据源**，微信自定义分析为备份与官方看板。

## 1. 埋点总体设计

### 1.1 采集架构

```
小程序页面/组件
    │  track(event, props)
    ▼
本地队列（最多 50 条）── 满 10 条或间隔 5s 或 onHide/onUnload ──► POST /api/app/events
    │
    ├─ 同时：核心事件 wx.reportEvent（P1 可后接，事件名与下表对齐）
    ▼
API：校验、去敏、写入 analytics_events
    │
    ├─ 实时：商品计数器 +1（expose/click/cart；pay 仅服务端）
    └─ 每日任务：汇总 goods_stats_daily，重算 heat_score
```

支付成功、退款、取消 **只由服务端写分析事件**，客户端可报 `pay_result`（用户取消 / 失败）用于漏斗，不作为购买率分子。

### 1.2 身份与会话（隐私）

| 字段 | 规则 |
|------|------|
| `anonymous_id` | 首次启动生成 UUID，存 Storage，卸载后会变 |
| `user_id` | 仅登录后带内部 ID，**事件表不存 openid / 手机号 / 昵称** |
| `session_id` | 冷启动生成；后台超过 30 分钟再进入视为新会话 |
| `scene` | `wx.getLaunchOptionsSync().scene` 及 `onShow` 的 scene |
| `utm` | 页面 query：`from` `share_uid` `goods_id` 等，用于社群归因 |

隐私协议须声明「用于改进商品展示与经营分析」；不把分析数据卖给第三方。管理端只出聚合与商品级指标，不提供「某用户浏览轨迹」给店员（P2 若做须单独权限）。

### 1.3 曝光认定（避免虚高）

小程序列表无完善 IntersectionObserver 时，采用 **保守曝光**：

- 商品卡 **进入可视区域**（`wx.createIntersectionObserver`，`thresholds: [0.5]`，相交 ≥ 50%）且停留 ≥ **300ms** 记一次曝光。
- 同一 `session_id` + `goods_id` + `slot_id` **30 秒内只报 1 次曝光**（客户端去重 + 服务端可再按分钟去重）。
- **禁止** 仅因接口返回列表就报曝光（否则 CTR 被严重低估或分母失真）。
- 详情页 `onShow` 记 `goods_detail_view`，与列表曝光分开，互不替代。

### 1.4 上报性能与失败

- 批量 JSON，单次 ≤ 20 条、body ≤ 32KB。
- 失败入本地重试队列，最多 3 次；不阻塞下单。
- 埋点接口 **允许未登录**；有 token 则绑定 `user_id`。
- 开发版可 `debug=1` 在 vConsole 打印，生产关闭。

### 1.5 公共属性（每条事件必带）

| 属性 | 说明 |
|------|------|
| `event` | 事件名，见事件字典 |
| `ts` | 客户端事件时间（毫秒） |
| `anonymous_id` / `session_id` | 见上 |
| `user_id` | 可空 |
| `page` | 路由路径，如 `pages/home/index` |
| `scene` | 微信场景值，可空 |
| `app_version` | 小程序版本号 |
| `query` | 进入页 query 中的业务参数（白名单：`id` `from` `slot` `share_uid` `keyword`） |

## 2. 小程序事件字典

优先级：**P0 随交易上线必须采集**；**P1 随推荐位 / 营销上线**；P2 增强。

### 2.1 应用与页面

| 事件名 | 触发 | 关键属性 | 优先级 |
|--------|------|----------|--------|
| `app_launch` | `App.onLaunch` | `scene` `query` `is_first_open` | P0 |
| `app_show` | `App.onShow` | `scene` `query` | P0 |
| `app_hide` | `App.onHide` | `session_duration_ms`（本次前台时长） | P0 |
| `page_view` | 每个页面 `onShow` | `page` `refer_page` | P0 |
| `page_leave` | `onHide` | `page` `stay_ms` | P1 |

### 2.2 商品曝光与点击（运营核心）

| 事件名 | 触发 | 关键属性 | 优先级 |
|--------|------|----------|--------|
| `goods_expose` | 卡片满足曝光规则 | `goods_id` `slot_id` `position` `page` | P0 |
| `goods_click` | 点击卡片进入详情 | `goods_id` `slot_id` `position` `page` | P0 |
| `goods_detail_view` | 详情 `onShow` 且商品存在 | `goods_id` `from_slot`（query） | P0 |
| `goods_detail_leave` | 详情 `onHide` | `goods_id` `stay_ms` | P1 |

`slot_id` 取值见第 5 章。`position` 从 1 起的坑位序号。

### 2.3 交易漏斗

| 事件名 | 触发 | 关键属性 | 优先级 |
|--------|------|----------|--------|
| `add_to_cart` | 加购成功（服务端成功后再报） | `goods_id` `qty` `from_page` `slot_id` | P0 |
| `buy_now_click` | 点击立即购买 | `goods_id` `qty` | P0 |
| `cart_settle_click` | 购物车「去结算」 | `sku_count` `amount_cent` | P0 |
| `order_submit` | 创建订单接口成功 | `order_no` `fulfill_type` `sku_count` `pay_amount_cent` `item_goods_ids` | P0 |
| `pay_invoke` | 调起 `wx.requestPayment` 前 | `order_no` | P0 |
| `pay_result` | 支付回调到小程序 | `order_no` `result`: `ok` / `cancel` / `fail` | P0 |
| `pay_success` | **仅服务端** 支付成功 | `order_no` `user_id` 及订单行 | P0 |
| `order_cancel` | 取消成功（端或服） | `order_no` `reason` | P0 |
| `rebuy_click` | 再买一单 | `order_no` `goods_ids` | P1 |

购买率分子 **只使用服务端 `pay_success` 对应的 `order_items`**（支付成功且未在统计窗口内全额退款的行；部分退 P1 按剩余件数）。

### 2.4 搜索、内容、履约、分享

| 事件名 | 触发 | 关键属性 | 优先级 |
|--------|------|----------|--------|
| `search_submit` | 提交关键词 | `keyword` `result_count` | P0 |
| `search_no_result` | 结果为 0 | `keyword` | P1 |
| `banner_expose` / `banner_click` | 轮播曝光 / 点击 | `banner_id` `position` | P1 |
| `category_click` | 点分类导航或左侧分类 | `category_id` | P1 |
| `share_click` | 触发分享 | `target_type` `goods_id?` | P1 |
| `contact_shop` | 拨打电话 / 复制微信 | `action` | P1 |
| `pickup_code_view` | 查看提货码 | `order_no` | P2 |

### 2.5 不采集（明确禁止）

- 输入框逐字内容（搜索只在提交时报 `keyword`）。
- 完整手机号、收货门牌、支付密码相关。
- 管理端操作轨迹（管理端另做审计日志，不属于本埋点表）。
- 高频 `scroll` / `touchmove`。

## 3. 指标字典（店主可见口径）

统计默认时区 **Asia/Shanghai** 自然日。管理端筛选项：今日 / 近 7 日 / 近 30 日 / 自定义（最长 90 日）。

### 3.1 商品过程指标

| 指标 | 计算 | 说明 |
|------|------|------|
| 曝光次数 `expose_pv` | `goods_expose` 计数 | 去重规则见 1.3 |
| 曝光人数 `expose_uv` | 去重 `user_id`，无则 `anonymous_id` | |
| 点击次数 `click_pv` | `goods_click` | |
| 点击人数 `click_uv` | 同上 UV | |
| **点击率 CTR** | `click_uv / expose_uv` | 主展示；另提供次数 CTR=`click_pv/expose_pv` 作对照 |
| 详情浏览 `detail_uv` | `goods_detail_view` UV | |
| 加购次数 / 人数 | `add_to_cart` | |
| **加购率** | `cart_uv / click_uv` | 分母为点击；点击为 0 显示「—」 |
| 支付件数 `pay_qty` | 支付成功订单行 `qty` 之和 | 服务端 |
| 支付人数 `pay_uv` | 支付成功且包含该 SKU 的用户数 | |
| 支付金额 | 订单行 `amount_cent` 之和（支付成功） | |
| **购买率 CVR** | `pay_uv / click_uv` | **主口径**；辅助口径 `pay_uv / detail_uv` |
| 曝光购买率 | `pay_uv / expose_uv` | 衡量坑位质量 |

**样本不足：**

- 看板展示：CTR / 曝光购买率在 `expose_uv < 10` 时标「样本少」；点击购买率 / 加购率在 `click_uv < 10` 时标「样本少」。
- 自动排序惩罚仍用窗口内 `expose_uv < 10` 或 `click_uv < 5`，**不作为降权项**（避免新上架被打入冷宫）。

购买率分子 **只使用支付回调成功** 的用户数，不使用客户端 `pay_success`。

### 3.2 商品热度 `heat_score`

面向店主的 **0–100 整数**，公式必须可解释，禁止纯黑盒。

**原始分（按窗口统计）：**

```
ctr_smooth = (click_uv + 2) / (expose_uv + 20)     # 弱先验约 10%
cvr_smooth = (pay_uv + 1) / (click_uv + 25)        # 弱先验约 4%，分子为支付人数

raw =
    0.08 * ln(1 + expose_uv)
  + 0.18 * ln(1 + click_uv)
  + 0.20 * ln(1 + cart_uv)
  + 0.34 * ln(1 + pay_uv)
  + 0.08 * ln(1 + pay_qty)
  + 0.07 * ln(1 + ctr_smooth * 100)
  + 0.05 * ln(1 + cvr_smooth * 100)
```

缩放用店内 **P95**（并与中位数×3 取较大者），避免单个爆款把其余商品压成 0：

```
heat_window = 100 * raw / max(p95(raw), median(raw)*3, ε)
```

三个窗口再混合（突出「最近在火」，并保留衰减记忆）：

```
heat_30d：近 30 日每日指标乘 0.5^(距今天数/7) 后求和再算 raw（半衰期 7 天）
heat_score = round(0.30 * heat_1d + 0.50 * heat_7d + 0.20 * heat_30d)
```

`heat_1d` / `heat_7d` 算法同 raw，窗口分别为今日与近 7 日。无数据时为 0。日批会用订单回填当日 `pay_uv`（去重用户）。

**人工权重不计入 heat_score 原值**，只进入排序分（见第 4 章），避免店主把权重拉满后看不懂「真实热度」。后台同时展示：真实热度、加权排序分。

每日 00:20 全量重算；日内对支付成功做 **增量刷新** 该 SKU 的 1 日热度（P1；P0 可仅日批）。

### 3.3 店级漏斗（工作台）

| 步骤 | 指标 |
|------|------|
| 打开小程序 | `app_launch` UV |
| 看到商品 | 有过 `goods_expose` 的 UV |
| 进入详情 | `goods_detail_view` UV |
| 加购 | `add_to_cart` UV |
| 提交订单 | `order_submit` UV |
| 支付成功 | 服务端支付成功 UV |

工作台展示各步转化率及环比（P1）。P0 工作台可只放待处理订单，本漏斗随 P1 看板。

### 3.4 异常经营信号（P1）

| 信号 | 条件（近 7 日，且样本足够） | 建议文案 |
|------|------------------------------|----------|
| 高曝光低点击 | CTR 低于全店中位数 50% 且曝光 UV≥30 | 检查主图、价格是否醒目 |
| 高点击低购买 | CVR 低于中位数 50% 且点击 UV≥20 | 检查详情、库存、规格、价格 |
| 热度高库存低 | heat 位于 TOP20% 且库存 ≤ 预警阈值 | 尽快补货，避免空卖 |
| 有库存无曝光 | 上架≥3 日、库存&gt;0、曝光 UV=0 | 未被分到坑位，考虑加入推荐或提高权重 |

## 4. 权重与综合排序

### 4.1 字段

| 字段 | 范围 | 默认 | 说明 |
|------|------|------|------|
| `manual_weight` | **-50 ~ +50** 整数 | 0 | 店主干预；正数提前、负数沉底 |
| `sort` | 整数 | 0 | **分类内兜底序**（V1.0 已有），权重与热度都缺数据时使用 |
| `on_sale` / `stock` | — | — | 下架不参与推荐；售罄可展示但排序沉底 |

不设 0–100「权重百分比」以免与热度分混淆。文案：**「排序加权（-50～50）」**。

### 4.2 排序分（列表「综合」默认）

```
rank_score = heat_score + manual_weight
```

并列时：`sold_count` 高者优先，再 `updated_at` 新者优先。

**硬性规则（先于分数）：**

1. `on_sale=0` 或不对顾客展示。
2. 售罄（`stock=0`）排在有货之后（仍可展示售罄卡）。
3. 推荐位置顶商品 **不受** `rank_score` 影响，按坑位序号（见第 5 章）。
4. 样本不足的新品：`heat_score=0` 时靠 `manual_weight` 与 `sort`、上架时间；新品保护：上架 **72 小时内** 额外 `+8` 热度等价分（只加到 `rank_score`，不加到展示用 `heat_score`），避免新货永远无曝光。

分类页排序选项：

| 选项 | 规则 |
|------|------|
| 综合（默认） | `rank_score` |
| 价格升/降 | 现价 |
| 销量 | `sold_count` |
| 上新 | `created_at` |
| 热度 | 仅 `heat_score`（忽略权重，给店主预览真实人气时小程序 **不展示此选项**；仅管理端「按热度预览」） |

小程序对顾客 **不出现「热度」二字**，避免费解；只保留「综合 / 价格 / 销量 / 上新」。

### 4.3 权重操作（管理端）

- 商品列表与编辑页可改加权；列表支持 **行内修改**（P1）。
- 批量：选中商品统一 +10 / -10 / 归零（P1）。
- 变更写审计日志（操作者、旧值、新值）。
- 保存后 **立即** 影响推荐拉取与综合排序（读库字段，无需等日批）。热度本身仍按日批/增量。

## 5. 推荐位需求

### 5.1 坑位清单

| slot_id | 位置 | 默认容量 | 优先级 | 填充策略默认 |
|---------|------|----------|--------|----------------|
| `home_banner` | 首页轮播 | 3–5 | P0 内容 / P1 统计 | 人工配置（已有 Banner） |
| `home_deal` | 首页特价专区 | 6–12 | P0 | 特价活动商品；不足不补或用权重最高有货特价 |
| `home_recommend` | 首页推荐 | **8**（可配 4–20） | **P1** | **置顶 + 热度补齐** |
| `category_list` | 分类右侧列表 | 分页 | P0 | 综合排序（热度+权重） |
| `search_result` | 搜索结果 | 分页 | P0 | 关键词匹配后按 `rank_score` |
| `detail_related` | 详情页「本店还买」 | 6 | P2 | 同分类热度 TOP，排除当前商品 |
| `cart_upsell` | 购物车凑单 | 4 | P2 | 热度高且未在车内 |

一期 **必须落地** 的推荐位是 `home_recommend` + 列表综合排序；特价 / 轮播沿用 V1.0。

### 5.2 首页推荐填充算法（P1）

输入：容量 `N`（默认 8），置顶列表 `pins[]`（有序），候选 = 上架且未删除。

```
result = []
1. 按 pin 顺序加入仍上架的商品（售罄可加入但标售罄，或跳过售罄——默认 **跳过售罄置顶** 并后台提示）
2. 若不足 N：从候选中排除已入选，按 rank_score 降序补齐
3. 仍不足：用上新补齐
4. 输出 N 条（可少于 N）
```

置顶 **最多 N 条**；超出拒绝保存。同一商品不能在同一 slot 置顶两次。

店主可切换策略（推荐位设置）：

| 策略 | 行为 |
|------|------|
| `PIN_THEN_HEAT` | 默认：置顶 + 热度补齐 |
| `PIN_THEN_SALES` | 置顶 + 销量补齐 |
| `PIN_THEN_NEW` | 置顶 + 上新补齐 |
| `MANUAL_ONLY` | 只展示置顶，不自动补（坑位可空） |

### 5.3 推荐位管理端交互

路由：`/content/recommends`（或 `/goods/recommends`）。

1. 选择坑位（先做首页推荐）。
2. 设置容量、策略。
3. **置顶商品**：搜索添加、拖拽排序、删除；展示当前热度 / CTR / 购买率便于决策。
4. **效果预览**：按当前算法列出将在小程序出现的 N 个商品（只读）。
5. 保存立即生效（小程序 bootstrap 与 `/home/*` 分块接口缓存 TTL ≤ 2 分钟，推荐接口建议 **不走 5 分钟店铺缓存**，或单独短缓存 60s）。

商品编辑页增加：

- 排序加权 `manual_weight`
- 快捷「置顶到首页推荐」（打开弹层选序号）

### 5.4 小程序展示

- 首页推荐模块标题可配，默认「本店推荐」。
- 无任何可展商品时 **整块隐藏**（与 V1.0 空态规则一致）。
- 卡片点击带 query `slot=home_recommend&pos=3`，便于 `goods_detail_view.from_slot` 归因。
- 不向顾客展示热度分数。

### 5.5 推荐位自身指标（P1）

每个 slot 在统计期：

- 模块曝光 UV（任意该 slot 的 `goods_expose`）
- 点击 UV、CTR
- 由该 slot 点击进入详情后 24h 内支付成功的 UV（归因：最后点击坑位 **last click**）

用于判断「首页推荐是否比分类列表更能卖货」。

### 5.6 「为你推荐」规则（非机器学习）

一期仍 **不上训练模型**。`GET /home/for-you` 用可解释规则：

1. 候选：上架有货，按热度 / 销量取 TOP 80（避免无序截断导致结果抖动）。
2. 得分：分类亲和 0.30（支付 0.55 + 近 30 日点击衰减 0.35 + 常购品类加成）+ 共购 0.16 + 热度 0.22 + 人工权重 0.12 + 近期点击 0.14 + 复购品类 0.06。
3. 杂货场景：近 3 日刚买过的 SKU 降权；90 日内买过 2 次以上的 SKU 加权（补货）。
4. 多样性：结果内同一分类最多 2 个（容量 ≤8 时），不足再回填。
5. 未登录：按热度 + 权重，仍做分类多样性。

## 8. 技术实现要点

### 8.1 小程序

- `utils/tracker.ts`：`track()`、队列、去重、IntersectionObserver 封装。
- 商品卡组件统一曝光与点击，禁止页面复制粘贴漏埋。
- `app.json` 声明隐私；自定义分析事件在微信后台配置与 P0 事件同名（P1）。

### 8.2 服务端（Node 16.17.0）

- 写入 `analytics_events` 用批量 insert；校验 event 枚举，过长 payload 截断。
- 日批：`node-cron` 00:20 汇总昨日 + 重算 `heat_score`。
- 限流：同一 IP 每分钟事件包 ≤ 120，防刷热度。
- 刷曝光作弊：同 `anonymous_id` 单日单商品曝光 &gt; 50 次截断计数。

### 8.3 管理端

- 商品分析表：MUI Table + 排序箭头；CTR 用 `LinearProgress` 或百分比文本。
- 推荐位置顶：可排序列表（上移下移按钮即可，一期不引入 dnd 库以降低 Node 16 依赖风险）。

## 9. 优先级与验收

### 9.1 分期

| 级别 | 范围 |
|------|------|
| **P0** | 事件字典中 P0 采集；`analytics_events` 落库；支付成功服务端计销售；商品卡曝光/点击规范。**无看板也可上线交易。** |
| **P1** | 商品分析页、热度分、权重、首页推荐位、综合排序、漏斗、异常信号、微信 `reportEvent` 双写 |
| **P2** | 详情关联推荐、购物车凑单、last-click 坑位归因报表、用户级轨迹、A/B |

### 9.2 验收用例

1. 预览版滑动首页，推荐卡进入可视区 ≥300ms 后库中有 `goods_expose`；快速滑过不记或极少。
2. 点击进入详情有 `goods_click` + `goods_detail_view`，`slot_id` `position` 正确。
3. 支付成功后，即使杀掉小程序，商品分析购买件数仍增加。
4. 将商品加权 +20，综合列表与推荐补齐顺序立刻前移。
5. 置顶 2 个商品，策略 `PIN_THEN_HEAT`，预览与小程序前 2 个一致，其后为热度补齐。
6. 样本不足商品率值不显示为 0% 吓人值，而显示「—」或「样本少」。
7. 事件接口不携带手机号；抽查 payload 无 openid。
